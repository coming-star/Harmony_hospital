### 2.2 缓存工具类扩展（📁 `common/RedisCacheUtil.java`）

新增 `deleteByPrefix` 方法，按前缀模糊批量删 key（号源缓存清理需要）：
```java
public void deleteByPrefix(String prefix) {
    Set<String> keys = stringRedisTemplate.keys(prefix + "*");
    if (keys != null && !keys.isEmpty()) {
        stringRedisTemplate.delete(keys);
        log.info("Redis 按前缀删除 {} 条 key, 前缀={}", keys.size(), prefix);
    }
}
```
> ⚠️ 注意：只能用窄范围前缀（如"精确到科室+日期"），生产环境不能写 `"*"` 这种宽查询，会阻塞 Redis 单线程。

#### B. 3 个 Service 的写操作都加了 `evictSlotCache()`

| Service | 方法 | 为什么要清 |
|---|---|---|
| **AdminScheduleRuleService** | create/update/toggleStatus/delete | 改了限额/时段/停用 → 号源立刻变 |
| **AdminDoctorService** | create/update/toggleStatus/delete | 换科室/换号别/停用医生 → 科室下医生列表变 |
| **AdminDepartmentService** | create/update/toggleStatus/delete | 停用内科 → 该科室号全部不能约 |

每个 Service 注入 `RedisCacheUtil`，定义统一前缀：
```java
private static final String SLOT_QUERY_CACHE_PREFIX = "his:cache:slotQuery:";

private void evictSlotCache() {
    redisCacheUtil.deleteByPrefix(SLOT_QUERY_CACHE_PREFIX);
}
```
然后在 4 个写操作末尾调用。`AdminDepartmentService` 原来已有 `evictDeptTreeCache()`，所以写操作末尾变成两行：
```java
evictDeptTreeCache();   // 清科室树
evictSlotCache();       // 清号源
```

### 2.5 已确认无需修改的部分

#### 全局异常处理器 ✅ 已就绪（📁 `common/GlobalExceptionHandler.java`）

已有 `@RestControllerAdvice`，包含 6 个 `@ExceptionHandler`，所以 Apifox 调接口遇到错误，返回一定是：

```http
HTTP 4xx / 5xx
Content-Type: application/json

{
  "code": 4xxxxx 或 HTTP状态码,
  "message": "具体中文错误提示",
  "content": null
}
```

| 异常类 | HTTP 状态码 | 业务来源举例 |
|---|---|---|
| `BusinessException(SLOT_SOLD_OUT)` | **409** CONFLICT | 号源被抢完 |
| `BusinessException(BUSINESS_RULE_VIOLATION)` | **422** UNPROCESSABLE_ENTITY | ❗限流 5 次 / Redis 锁没抢到(重复挂号) |
| `BusinessException(ORDER_STATUS_CONFLICT)` | **409** | 取消已取消的订单 |
| `BusinessException(REFERENCED_BY_OTHER_RECORD)` | **409** | 删有关联的科室/医生/规则 |
| `ResponseStatusException(404)` | **404** | 号源不存在 / 就诊人不存在 |
| 参数校验异常 | **400** | 请求体字段不合法 |
| 其他未捕获异常 | **500** | 兜底（日志记录堆栈） |

> ❗限流和重复挂号返回的 HTTP 状态码是 **422**，不是 429 Too Many Requests；因为这两类错误都走 `ErrorCode.BUSINESS_RULE_VIOLATION`（HttpStatus 是 UNPROCESSABLE_ENTITY 422）。老师问起来可以说是"统一归入业务规则校验错误 422"，如果想严谨点改成 429，可以在 ErrorCode 新增 `TOO_MANY_REQUESTS(429001, HttpStatus.TOO_MANY_REQUESTS, "操作过于频繁")` 并让限流改用它——不改也没问题，功能一样，只是语义差异。

## 三、附：Apifox 验证限流 + 全局异常的操作步骤（给用户 11 条的回答）

**测试的是：`POST /api/app/orders` 患者下单挂号接口**。

### 步骤

1. **先准备一条正常请求能跑通**（保证 token、slotId、contactId、idempotencyKey 都对）
2. Apifox 把这个接口请求 **Ctrl+C 复制一份** 到 Apifox 的快速请求里（或同一个 tab）
3. 保持参数不变（**尤其是 `idempotencyKey` 可以每次手动换新的**，否则幂等键拦的就是同一个，看不到限流效果！）
4. **连续点发送按钮 6 次**（或 Apifox 里 Runner 跑并发）

### 看哪里的响应

Apifox 右侧的 **"实际响应"** 面板：
- 前 5 次 → 正常下单成功，2xx
- **第 6 次** → 你需要看这三个地方：

| 看哪里 | 正确结果（配置对了） | 错误结果（没生效/崩了） |
|---|---|---|
| Apifox 左上角 **HTTP 状态码**（蓝色标签） | **422**（Unprocessable Entity） | **500** Internal Server Error 或 白页 Whitelabel Error Page |
| 响应 Body 选项卡 → **Pretty** | JSON 格式，`message` 是中文 | HTML 源码（Spring 默认错误页） |
| JSON 里的 `message` 字段 | `"操作过于频繁，请 1 分钟后再试（每分钟最多 5 次）"` | 不是中文，或 message 是 `"系统繁忙"`（走了 500 兜底） |

**注意**：限流每分钟归零一次——测完第 6 次后，要等 **60 秒** 再测下一轮，不然一直被拦。
