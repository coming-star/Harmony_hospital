# 项目总结

> 版本：v1.0 ｜ 更新日期：2026-09-06
>
> 项目：东软云医院预约挂号系统（鸿蒙 App + Web 管理端 + Spring Boot 后端 + DeepSeek AI 导诊）

## 1. 项目概况

面向患者与医院管理员的预约挂号系统。患者通过鸿蒙 App 完成从浏览科室、选择医生与时段、确认预约、模拟支付到取消退号的完整闭环，并可用 AI 导诊助手进行症状咨询与科室推荐；管理员通过 Web 后台维护科室、医生、号别、排班规则，查看运营统计并处理订单。

技术栈：Spring Boot 3 + MyBatis-Plus + MySQL 8 + Redis 7 + JWT（后端），Vue 3 + Element Plus（管理端），HarmonyOS ArkTS / ArkUI（移动端），DeepSeek 大模型（AI 导诊）。

## 3. 技术亮点

- **规则与号源分离**：排班规则只做周期模板，患者对号源下单；号源自动滚动生成，管理员无需逐日录号。
- **四层防超卖**：限流挡刷 → 分布式锁挡重复挂号 → 幂等键挡重试 → 乐观锁条件更新做数据库兜底，各层职责清晰。
- **订单快照设计**：下单时刻冗余医生/科室/号别/时间，历史订单不受基础资料变更影响。
- **无状态 AI 接入**：用 JDK 内置 HttpClient 直连 DeepSeek，零额外依赖；Key 只存后端，前端不接触。
- **设计令牌统一**：鸿蒙端颜色/字号/间距/圆角全部从 `color.json`/`float.json` 引用，杜绝硬编码。

## 4. 踩坑与复盘

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 点"确认订单"加载中后无反应、预约记录不生成 | 雪花 ID（19 位）超过 JS 安全整数 2^53，前端 `JSON.parse` 后精度丢失，传给后端的 contactId 错误，返回"就诊人不存在" | 后端 ID 加 `@JsonSerialize(ToStringSerializer)` 序列化为字符串；前端 slotId/contactId/orderId 全链路按 string 传递，禁止 `Number()` |
| Git 合并后部分功能丢失 | 多人 feature 分支合并时冲突解决误选了旧代码 | 用 `git diff <合并提交> <对方分支>` 逐文件对比合并结果与源分支，定位并恢复 |
| Redis 缓存序列化异常 | 把 MyBatis-Plus 的 `Page` 分页对象塞进缓存 | 缓存只存 `List` 或普通 VO，不存框架分页对象 |
| 删除确认弹窗被拉成全屏 | 弹窗文字容器上有 `layoutWeight(1)`，在全屏遮罩里把卡片纵向撑满 | 移除 `layoutWeight`，弹窗外包撑满居中容器 |
| 删除弹窗、就诊人弹窗底色不一致 | 不同弹窗分别设了白色和灰底 | 统一使用 `sheet_bg = #F1F3F5` 资源 |
| 鸿蒙构建内存不足（`hs_err_pid`） | 后端常驻占内存，打包 JVM 堆不够 | 构建时关闭后端进程或调大虚拟内存；错误日志加入 `.gitignore` |
| 已支付订单无法取消 | 后端只允许待支付订单取消 | 取消逻辑放宽到待支付/已支付均可（已支付=退号，号源回补） |

## 5. 暂未实现功能（按实现难度由易到难排序）

> 以下功能本期未实现，部分已在数据库或接口上预留扩展位置。后续优化可按本表顺序推进。

### ~~5.1 上传头像、修改昵称等账号资料管理~~ ✅ 已实现

- **难度**：★ 简单
- **实现情况**：后端 `PUT /api/me` 更新昵称/头像；`POST /api/upload/avatar` 支持 jpg/jpeg/png/webp（≤5MB），本地存储 + `/static/avatars/**` 静态映射；前端个人中心头像可点击上传、昵称可点击弹窗修改，UserStore 持久化头像 URL。

### ~~5.2 身份证实名采集~~ ✅ 已实现

- **难度**：★★ 较易
- **实现情况**：就诊人新增/编辑表单加身份证输入（18 位校验）；后端 AES-GCM 加密存储密文、SHA-256 哈希做同账号判重；列表仅返回脱敏值（前 3 后 4），明文绝不回显；编辑时不传 `idCard` 保留原值、传空串清除。

### 5.3 AI 会话持久化

- **难度**：★★ 较易
- **现状**：`ai_conversation` / `ai_message` 表已建但代码未使用；当前多轮对话由客户端每次携带完整消息列表，服务端无状态，App 杀进程后历史丢失。
- **改造点**：`AiService` 增加会话 CRUD，按 `user_id` 隔离；首次对话创建会话并落库历史消息；返回 `conversationId` 供前端带入后续请求。

### 5.4 AI 流式输出（SSE）

- **难度**：★★★ 中等
- **现状**：当前 `stream=false`，一次性返回完整回复，长回复等待时间长。
- **改造点**：调用 DeepSeek 时 `stream=true`，用 `HttpClient` 读取 chunked 响应，后端以 SSE 推给前端，前端逐字渲染。

### 5.5 短信验证码登录 / 找回密码

- **难度**：★★★ 中等
- **现状**：当前只有手机号 + 密码登录，无验证码通道。
- **改造点**：接入短信服务商 SDK（如阿里云短信）；`/api/app/auth/sms-code` 发送并在 Redis 存 5 分钟；登录/注册/找回密码接口校验验证码；同手机号 60 秒内限发。

### 5.6 消息推送

- **难度**：★★★ 中等
- **现状**：订单状态变更（支付成功、取消、超时）仅靠患者主动刷新查看。
- **改造点**：接入鸿蒙 Push Kit 或极光推送；订单状态变更时触发推送；管理端可用站内信或邮件通知。

### 5.7 医生临时停诊 / 加号的管理端可视化操作

- **难度**：★★★ 中等
- **现状**：号源 `status` 字段支持 `OPEN`/`CLOSED`/`CANCELLED`，但管理端没有停诊/加号入口，改号源只能直接操作数据库。
- **改造点**：管理端加"号源管理"页，可按医生+日期查看号源，支持临时加号（INSERT 一条 `schedule_rule_id=NULL` 的号源）、停诊（status 改 CLOSED，已下单订单需批量取消并回补）。

### 5.8 真实微信 / 支付宝支付

- **难度**：★★★★ 较难
- **现状**：`payment_record` 表已预留 `channel`、`trade_no` 字段；当前 `channel=MOCK` 模拟支付。
- **改造点**：接入微信支付/支付宝 SDK 与沙箱；下单时创建预支付订单返回支付参数；客户端拉起支付 SDK；后端接收异步回调并验签更新订单；已支付订单取消时走退款接口。

### 5.9 AI 实时号源查询（Function Calling）

- **难度**：★★★★ 较难
- **现状**：AI 只能回答通用科室/流程问题，不知道"明天心血管内科还有没有号"。
- **改造点**：实现 DeepSeek 的 Function Calling（tool_calls）；后端暴露"按科室+日期查号源"工具；AI 判断需要实时信息时调用工具并整合到回复。

### 5.10 AI 辅助下单（不自动扣费）

- **难度**：★★★★ 较难
- **现状**：AI 只做咨询引导，不能产生订单。
- **改造点**：AI 收集患者意图（科室、日期、就诊人）后生成**预约草稿**，推送到前端由患者确认并进入正常下单/支付流程；AI 永远不直接调下单接口、不触发扣费。

### 5.11 RocketMQ 事件总线

- **难度**：★★★★★ 较难
- **现状**：订单超时取消用 `@Scheduled` 定时任务（每 60 秒扫描），存在最长 60 秒的延迟；订单状态变更无事件通知。
- **改造点**：引入 RocketMQ；下单时发送延迟消息（15 分钟）替代定时扫描；订单状态变更发布事件，供推送、统计等消费方订阅；事务消息保证"订单落库"与"消息发送"原子性。
