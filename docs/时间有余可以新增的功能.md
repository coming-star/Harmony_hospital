## 一、登录/注册接口限流（★☆☆，20 分钟）

### 为什么要做
脚本最容易爆刷的就是登录接口——黑客拿常见密码字典循环试（`123456`、`admin123`、`password`…），一秒钟能试几百个，弱密码几分钟就被撞开。注册接口也可能被批量刷垃圾账号。

### 怎么做（和挂号限流同一个模板，已经写过一遍了）
在 `AppAuthController` 的 login 方法（或 AuthService 里）开头加：

```java
// 限流：每个手机号每分钟最多试 5 次登录
String limitKey = "auth:login:limit:" + phone + ":"
        + LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmm"));
long count = redisCacheUtil.increment(limitKey, 60);
if (count > 5) {
    throw new BusinessException(ErrorCode.BUSINESS_RULE_VIOLATION,
            "密码错误次数过多，请 1 分钟后再试");
}
```

注册接口同理（key 用 IP 或手机号）。`RedisCacheUtil.increment` 是现成的。

### 注意
- 登录失败才计数还是每次都计数？简单做法：**每次请求都计数**（防的就是暴力试，失败成功都算）。
- key 维度用手机号：黑客试一个手机号 5 次后锁定，不影响其他正常用户。

## 二、空值缓存防缓存穿透（★☆☆，30 分钟，Redis 作业加分项）

### 什么是缓存穿透
反复查询一个**数据库里根本不存在**的数据（比如恶意构造不存在的科室 id），缓存永远没有 → 每次都打到 MySQL。

### 空值缓存做法（简单版，推荐）
查科室树/号源时，如果数据库查出来是空的，也往 Redis 写一个占位值，TTL 设短一点（1 分钟）：

```java
List<Slot> slots = 查数据库();
if (slots.isEmpty()) {
    redisCacheUtil.set(cacheKey, "NULL", 60);   // 空结果也缓存 1 分钟
} else {
    redisCacheUtil.set(cacheKey, JSON.toJSONString(slots), 300);
}
```
读取时发现是 `"NULL"` 就直接返回空列表，不碰数据库。

### 布隆过滤器做法（难，不建议本期做）
引入 Guava/Redisson 的 BloomFilter，把所有存在的 id 预热进去，查询前先问过滤器"这个 id 可能存在吗"，说不可能就直接返回。
难点：过滤器要预热、数据增删时要同步维护、位数组大小和误判率要调参，讲不清楚反而被老师问住。

## 三、`@RateLimit` 注解 + AOP 限流（★★★，约 1 天，Redis 作业高分项）

### 效果
现在限流代码写死在 OrderService 里，抽成注解后任何接口一行注解就能限流：

```java
@PostMapping
@RateLimit(limit = 5, windowSeconds = 60, keyPrefix = "reg:limit:")
public ApiResponse<OrderDetail> create(...) { ... }

@PostMapping("/login")
@RateLimit(limit = 5, windowSeconds = 60)   // 登录也直接加上
public ... login(...) { ... }
```

### 要写的东西
1. 自定义注解 `@RateLimit(limit, windowSeconds, keyPrefix)`
2. 一个 `@Aspect` 切面类：`@Around` 拦截带注解的方法，用 SpEL 表达式从方法参数里取 userId/phone 拼 key，调 `redisCacheUtil.increment`，超限抛 BusinessException
3. 把 OrderService 里现有的限流代码删掉，改成注解

### 坑点（没写过 AOP 容易卡）
- 切点表达式 `@annotation(rateLimit)` 写法
- 从方法参数里取动态值（userId 在 Authentication 对象里），要会用 `JoinPoint.getArgs()` 或 SpEL
- 自测要写 AOP 生效的集成测试，光看代码看不出问题

## 四、就诊人身份证 AES-GCM 加密收集（★★☆，半天）

### 现状
就诊人模块（`/api/contacts`）已实现列表/新增/修改/删除，但表设计里的 `id_card_cipher`（密文）和 `id_card_hash`（哈希）两列暂时允许为空——本期演示不收集身份证号。

### 完整版做法
1. `ContactRequest` 加 `idCard` 字段（身份证号，前端选填或必填）
2. 新增时：
   - `id_card_hash` = SHA-256(身份证号)，用于同一账号下"身份证已绑定"查重（错误码已有：`CONTACT_ID_CARD_DUPLICATED 409002`）
   - `id_card_cipher` = AES-GCM 加密后的字节，密钥放配置文件，**绝不存明文**
3. 查询列表时不返回密文/哈希；需要展示身份证时只返回脱敏后的（如 `110***********1234`）
4. 为什么密文不能直接查重：AES-GCM 每次加密带随机 IV，同一明文两次加密结果不同，所以必须额外存一个哈希列做等值判断。
