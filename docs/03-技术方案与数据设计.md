# 技术方案与数据设计

## 1. 架构与模块

```
HarmonyOS App ─┐                         ┌─ MySQL 8（持久化）
Vue 管理后台 ──┼─ HTTPS / REST ─ Spring Boot ┼─ Redis（缓存、余号锁、JWT黑名单）
               │                         └─ RocketMQ（超时取消、通知事件）
               └──────────────────────────── LLM 网关（可选，AI 管家）
```

后端按 `auth`、`user`、`department`、`doctor`、`schedule`、`registration`、`admin`、`ai` 划分业务包。优先选定一种 ORM（建议 MyBatis-Plus），全项目不得混用两种 ORM；统一返回体 `ApiResponse<T>`、全局异常处理、分页对象和审计字段。

## 2. 核心数据表

所有业务表建议包含：`id`（bigint）、`created_at`、`updated_at`、`deleted`（tinyint，逻辑删除）。金额字段均以 `*_fen bigint` 保存。

| 表 | 核心字段 | 说明 |
| --- | --- | --- |
| `sys_user` | phone, password_hash, nickname, avatar, role, status, last_login_at | 患者和管理员账号；phone 唯一。 |
| `patient_contact` | user_id, name, id_card_cipher, id_card_hash, phone | 就诊人；身份证加密存储，哈希用于唯一性校验。 |
| `department` | code, name, parent_id, type, description, sort_no, enabled | `parent_id=0` 为一级科室。 |
| `registration_level` | code, name, fee_fen, quota, sort_no, enabled | 如普通号、专家号。 |
| `doctor` | name, department_id, title, avatar, introduction, enabled | 医生基础档案。 |
| `doctor_level` | doctor_id, level_id | 医生可提供的号别，多对多。 |
| `schedule_rule` | doctor_id, weekdays, period, start_time, end_time, slot_minutes, quota, enabled | 规则串可由上述字段序列化生成。 |
| `schedule_slot` | doctor_id, department_id, level_id, visit_date, start_at, end_at, total_quota, remaining_quota, enabled, version | 实际可预约号源；提前生成未来 7 天。 |
| `registration_order` | order_no, user_id, contact_id, slot_id, level_id, amount_fen, status, expired_at, paid_at, cancel_reason | 挂号订单；order_no 唯一。 |
| `payment_record` | order_id, channel, trade_no, amount_fen, status, paid_at | 本期 `channel=MOCK`。 |
| `ai_conversation` / `ai_message` | user_id, title / conversation_id, role, content | 内容须设长度限制并可按用户清理；AI 接入密钥统一走后端配置，不做个人配置表。 |

建议索引：`schedule_slot(doctor_id, visit_date, level_id)`、`schedule_slot(department_id, visit_date, enabled)`、`registration_order(user_id, status, created_at)`、`registration_order(slot_id, status)`，以及 `patient_contact(user_id, id_card_hash)` 唯一索引。

## 3. 预约并发方案

1. 查询页只读取 `remaining_quota`，不承诺提交时仍有余号。
2. 提交时校验日期、医生/号别/就诊人和重复预约，再使用 SQL 条件更新：`remaining_quota = remaining_quota - 1 where id=? and remaining_quota>0 and version=?`。
3. 更新成功后，在同一事务写入待支付订单和超时消息；失败则返回“号源已抢完”。
4. 支付成功或取消时按订单状态做条件更新，确保重复点击/消息重投不会重复扣减或归还。

Redis 仅用于热点缓存与可选分布式锁，MySQL 条件更新是最终正确性依据。RocketMQ 延迟消息在本期用于 15 分钟超时取消；消费者必须幂等。

## 4. REST 接口边界（首版）

| 分组 | 示例接口 |
| --- | --- |
| 鉴权 | `POST /api/auth/register`、`POST /api/auth/login`、`POST /api/auth/logout` |
| 患者/就诊人 | `GET /api/me`、`PUT /api/me`、`GET/POST /api/contacts`、`PUT/DELETE /api/contacts/{id}` |
| 号源查询 | `GET /api/departments/tree`、`GET /api/slots?departmentId&date&levelId`、`GET /api/doctors/{id}` |
| 预约 | `POST /api/orders`、`POST /api/orders/{id}/pay`、`POST /api/orders/{id}/cancel`、`GET /api/orders`、`GET /api/orders/{id}` |
| 后台 | `/api/admin/users`、`/departments`、`/doctors`、`/schedule-rules`、`/levels`、`/orders` 的分页 CRUD |
| AI | `POST /api/ai/chat`、`GET /api/ai/conversations` |

列表统一返回 `{ records, total, page, size }`；写接口返回资源或其 `id`。删除接口是逻辑删除，返回成功并不代表物理移除。

## 5. AI 管家边界

AI 接入的 URL、API Key、模型由后端统一配置（写在部署环境变量/配置文件中），不提供患者个人配置入口，避免要求患者自行准备密钥。后端使用工具化查询接口检索号源，而非让模型编造数据。意图为“预约”时，AI 仅返回包含医生、时段、就诊人的预约草稿/深链；患者必须进入预约确认页并支付。界面应提示“AI 建议不构成医疗诊断，紧急情况请及时就医”。
