## 2. 项目概述

### 2.1 项目背景

传统线下医院就诊存在患者现场排队耗时长、医生排班与号源信息不透明、流程繁琐等痛点；医院侧人工管理科室、医生、预约订单效率低、统计混乱。本系统搭建线上挂号预约平台：鸿蒙移动端为用户提供便捷线上就诊服务，Web 后台为管理员提供全流程数据管理能力，实现就医数字化、管理智能化。

### 2.2 项目目标

- **用户端（鸿蒙 APP）**：科室浏览、在线预约挂号、支付、就诊人管理、预约记录管理、AI 智能导诊，简化就诊流程。
- **管理端（Web 后台）**：科室、医生、排班、预约订单、用户账号的全流程管理，支持增删改查、筛选统计。
- **系统层面**：前后端分离，标准化 RESTful 接口，支持高并发预约场景，保证稳定性、数据一致性与安全性。

### 2.3 角色定义

| 角色 | 使用终端 | 核心权限 |
|---|---|---|
| 用户 | 鸿蒙 APP | 手机验证码注册/登录、浏览两级科室与医生、按时间查可约号源、在线预约、支付、查看/取消预约、就诊人管理、AI 症状导诊 |
| 管理员 | Web 后台 | 账号密码登录、两级科室管理、医生管理、排班配置、预约订单管理与强制取消、退号审核、用户账号管理、数据统计 |

## 3. 关键概念与设计约定

### 3.1 关键概念

| 概念 | 定义 | 关键点 |
|---|---|---|
| **用户（user）** | 登录账户，操作软件的人 | 手机注册自动生成，默认普通用户；管理员 role=9 |
| **就诊人（patient）** | 实际看诊的人，实名就医档案 | 必须有身份证；一个用户可绑多个就诊人（本人/父亲/母亲），挂号记就诊人，看诊核验就诊人本人身份证 |
| **医生（doctor）** | 医院出诊人 | 管理员按工号录入，非用户注册 |
| **职称 vs 号别** | 职称仅展示；号别（普通/专家/急诊）决定挂号费用 | 同一医生可同时有"专家号排班（贵）"和"普通号排班（便宜）" |

易混淆点：
- **用户 ≠ 就诊人**：用户是操作人，就诊人是实际就医人。张三帮父亲挂号 → `appointment.user_id=张三, patient_id=父亲`。
- **订单状态与支付状态分开维护**：订单状态描述预约生命周期，支付状态描述资金状态。

### 3.2 设计约定

| 项 | 约定 |
|---|---|
| 支付体系 | 有支付体系，超时未支付自动释放订单 |
| 预约路径 | **先选时间（日期 + 时段）再选医生** |
| 订单状态 | **4 态**：待支付 / 已预约 / 已取消 / 已完成 |
| 科室层级 | **两级关联**（一级大科 → 二级专科） |
| 号别费用 | 普通 / 专家 / 急诊费用不同 |
| 登录方式 | **手机验证码登录**（未注册自动注册）+ 管理员账号密码登录 |
| 号源粒度 | **只到"上午/下午"时段，不精确到具体几点**，无具体时间点排班 |
| 表命名 | 系统用户表用 `user`（Entity `User`）；MySQL 中 `user` 非保留字，建表/查询用反引号 `` `user` `` 规避与 `USER()` 函数、`mysql.user` 系统表混淆 |
| 通用字段 | 所有业务表含 `id/deleted/create_time/update_time`；金额 `decimal(10,2)`；状态 `tinyint`；`deleted` 为 bigint（软删置 id），唯一键用 `(业务键, deleted)` |

## 5. 核心业务流程

### 5.1 注册与登录（手机验证码）

1. 输入手机号获取验证码（开发期模拟码，生产接短信通道），验证码存 Redis（5 分钟有效）；
2. 输入验证码提交登录，校验验证码；
3. 未注册：自动创建 `user` + 默认"本人"`patient` + 绑定，完成注册；已注册：直接登录；
4. 登录成功返回 JWT Token。

### 5.2 预约挂号主流程（先选时间再选医生）

1. 登录 → 预约页；
2. 选一级科室 → 二级科室；
3. **先选日期 + 时段（上午/下午）**；
4. 展示该时段有排班的医生（号别、剩余名额、挂号费），可按号别筛选，名额为 0 不可选；
5. 选可约医生 → 确认就诊人（默认本人，可切换已绑定就诊人）；
6. 后端**下单预占号源**：创建订单（待支付），排班 `locked_num + 1`；
7. 支付挂号费；支付成功：订单 → 已预约，排班 `remain_num - 1`、`locked_num - 1`，生成排队号；
8. 完成，"我的预约"可查看。

### 5.3 支付与超时释放

1. 下单生成待支付订单并预占号源；
2. 订单进入超时倒计时（如 15 分钟，RocketMQ 延迟消息）；
3. 超时仍未支付：消息触发，订单仍为待支付 → 置为**已取消（原因：超时未支付）**，释放预占 `locked_num - 1`；已支付/已取消则幂等忽略；
4. 支付成功则消息触发时发现已支付直接忽略（与回调竞态用订单状态/version 兜底）。

### 5.4 取消预约与退费

1. 在"我的预约"选择可取消订单（待支付/已预约）；
2. 未支付：订单 → 已取消，释放预占 `locked_num - 1`；
3. 已支付：订单 → 已取消 + 生成退费记录（管理员审核/自动退）+ 返还号源 `remain_num + 1`，支付状态 → 已退款；
4. 号源释放后若有余量，排班状态自动恢复"可约"。

### 5.5 AI 管家

1. 点"AI 管家"，未登录提示登录；
2. 三类对话：①推荐可约医生（时间+科室）；②症状导诊（匹配科室）；③代预约（解析科室+时间+号别，复用 §5.2 统一预约+支付流程，完成提示支付按钮）。

## 6. 订单状态机

### 6.1 订单状态（appointment.status）—— 4 态

| 状态值 | 状态名 | 含义 | 可执行操作 |
|---|---|---|---|
| 0 | 待支付 | 已下单预占，未支付 | 支付、取消（释放预占）、超时自动取消 |
| 1 | 已预约 | 支付成功，待就诊 | 取消（退费+返还号源） |
| 2 | 已取消 | 用户取消/超时未支付/管理员强制取消 | 无 |
| 3 | 已完成 | 已就诊完成 | 无 |

### 6.2 支付状态（appointment.pay_status / pay_order.pay_status）

0-待支付 / 1-已支付 / 2-已退款 / 3-退款中

### 6.3 状态流转

```
创建订单(待支付, 预占locked+1)
  ├─ 支付成功 → 已预约(remain-1, locked-1, 生成排队号) → 就诊完成 → 已完成
  ├─ 用户取消(未付) → 已取消(释放locked-1)
  ├─ 超时未支付 → 已取消(原因=超时未支付, 释放locked-1)
  └─ 已预约 → 取消(已付) → 已取消 + 退费 + 返还号源(remain+1)
```

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 常规接口响应 ≤ 500ms；科室、医生等热点数据 Redis 缓存 |
| 并发 | 预约核心接口高并发下"DB 条件更新预占 + 乐观锁兜底"防号源超卖 |
| 异步 | 预约成功通知、超时释放、退款经 RocketMQ 异步处理，不阻塞主流程 |
| 安全 | 密码 BCrypt；JWT + Redis 登录态鉴权；跨域配置；数据权限隔离（用户仅见个人数据） |
| 可用性 | 核心预约流程操作 ≤ 5 步；鸿蒙端适配不同尺寸设备 |
| 可维护性 | controller/service/mapper 分层；关键代码注释；Knife4j 接口文档 |
