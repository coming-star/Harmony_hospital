# 01 需求分析文档

| 项目 | 内容 |
| --- | --- |
| 名称 | 东软云医院预约挂号系统 |
| 目标 | 让患者在鸿蒙 App 完成登录、就诊人管理、查询号源、预约及订单查询；让管理员维护基础医疗资源与挂号规则。 |
| 交付形态 | Spring Boot REST 服务、Vue 管理后台、HarmonyOS App、项目文档与演示数据。 |
| 周期 | 10 天：第 1 天环境搭建；第 2–8 天开发联调；第 9–10 天测试、答辩和面试准备。 |

> 版本：v1.0（交付版） ｜ 更新日期：2026-09-05

## 1. 项目背景

医院门诊挂号长期存在"排队久、跑腿多、号源不透明"的问题。本项目面向**患者**和**医院管理员**两类用户，构建一套预约挂号系统：

- 患者通过**鸿蒙手机 App** 完成注册登录、浏览科室医生、查看号源、预约挂号、模拟支付、管理就诊人，并可使用 **AI 导诊管家**进行症状咨询与科室推荐；
- 管理员通过 **Web 后台**维护科室、医生、号别、排班规则，处理挂号订单并查看运营统计。

系统采用前后端分离 + RESTful API 架构，后端为 Spring Boot 单体服务，同时服务鸿蒙端与 Web 管理端。

## 2. 用户角色与权限边界

| 角色 | 入口 | 权限边界 |
| --- | --- | --- |
| 游客 | 鸿蒙 App（未登录） | 浏览首页、科室和医生信息；可以注册、登录；进入预约、就诊人、AI 管家等功能时被引导先登录 |
| 患者（PATIENT） | 鸿蒙 App | 管理本人资料与名下就诊人；查询可预约号源；创建预约、模拟支付、取消订单（待支付/已支付均可退号）；查看本人挂号记录；使用 AI 导诊管家。**不能**访问任何 `/api/admin/**` 后台接口 |
| 系统管理员（ADMIN） | Web 管理后台 | 登录后台；维护用户、科室、医生、挂号级别、排班规则；查看全部挂号记录并取消订单；查看工作台统计看板。**不通过**患者 App 下单 |
| AI 导诊 | App 内嵌能力 | 用自然语言回答挂号与就诊流程问题、根据症状推荐科室、引导完成预约，降低使用门槛；仅作信息咨询和预约引导，**不输出医疗诊断结论、不查询实时号源**，也不能绕过患者确认直接下单或扣费 |

### 3.3 系统级能力（对用户不可见但必须具备）

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| SYS-01 | 号源自动生成 | 管理员只需维护"周一三五上午"这样的**排班规则**；系统在应用启动时和每天 00:10 自动把规则展开成未来 14 天内**每一天的具体可约时段**（即号源），患者看到的可约号源就是这样来的，无需人工逐日录入；重复执行不会生成重复号源 |
| SYS-02 | 并发防超卖 | 下单四层防护：Redis 限流（5 次/分钟）→ Redis 分布式锁（防同一就诊人重复挂号）→ 幂等键唯一约束（防重试重复下单）→ 号源乐观锁条件更新（防超卖的数据库兜底） |
| SYS-03 | 超时自动取消 | 待支付订单 15 分钟未支付，RocketMQ 延迟消息驱动自动取消并释放号源（定时任务 5 分钟一轮兜底） |
| SYS-04 | 缓存 | 科室树、号源查询等热点数据使用 Redis Cache-Aside 缓存，数据变更时主动失效 |
| SYS-05 | 大 ID 精度保护 | 雪花算法 ID 超过 JS 安全整数范围，后端统一序列化为字符串返回，前端全链路按字符串传递 |

## 5. 非功能性需求

| 类别 | 要求 |
| --- | --- |
| 一致性 | 同一时刻多人抢同一最后号源不得超卖；重复点击/网络重试不得生成重复订单 |
| 安全性 | 密码 BCrypt 加密存储；接口 JWT 鉴权；AI Key 只存后端；身份证字段预留 AES-GCM 加密位 |
| 可维护性 | 统一响应体 `ApiResponse<T>`、全局异常处理、统一错误码；前端设计令牌集中管理，禁止硬编码色值/字号 |
| 可移植性 | 主键使用雪花算法，为以后分库分表留余地 |
| 兼容性 | 移动端 HarmonyOS（ArkTS/ArkUI）；管理端 Chrome/Edge 现代浏览器 |

# 02 数据设计文档

> 建表脚本：`Hos_App/his-springboot/src/main/resources/db/01_schema.sql`
> 演示数据：`Hos_App/his-springboot/src/main/resources/db/02_demo_seed.sql`

## 0. 设计结论

数据库名称 `neusoft_cloud_hospital`，MySQL 8.0+（开发固定 8.0.36），字符集 `utf8mb4`。执行 `01_schema.sql` 建库建表后，可执行 `02_demo_seed.sql` 导入演示资料：管理员 `admin / admin123`、患者账号（手机号 `13800000002`~`13800000007`，密码均为 `password`）、28 个科室、24 位医生、5 种号别、18 条排班规则；应用启动后号源生成器会自动把号源滚动补充到未来 14 天。

**分层模型**：基础资料（科室/医生/号别）→ 排班规则（周期模板）→ 号源（每日可约时段）→ 挂号订单。排班规则本身不可直接预约，患者只能对号源 `schedule_slot` 下单，余号、停诊、并发控制都落在号源表上。

| 维度 | 取值 |
| -------- | --------------------------------------------------------- |
| 数据库类型 | MySQL 8.0.36 Community Server |
| 字符集 / 排序 | utf8mb4 / utf8mb4_0900_ai_ci |
| 存储引擎 | InnoDB（事务、行锁、CHECK 约束） |
| 主键生成 | 应用层雪花算法 `BIGINT UNSIGNED`，不用自增，便于未来分库分表 |
| 金额存储 | 整数"分"（`500` = ¥5.00），前端只负责格式化展示 |
| 逻辑删除 | 需保留历史的表带 `deleted TINYINT DEFAULT 0`，删除只置 1 |
| 审计字段 | 统一 `created_at` / `updated_at`，MySQL 默认值 + ON UPDATE 自动维护 |
| 物理外键 | **不建物理外键**（降低逻辑删除/批量导入/号源生成的耦合），关联完整性由 Service 层 + 索引保证 |
| 大 ID 传输 | 雪花 ID 超过 JS 安全整数（2^53），接口统一序列化为**字符串**返回，前端全链路按字符串传递 |
| 敏感字段 | 就诊人身份证 AES-GCM 密文 + SHA-256 哈希列；AI 密钥仅存环境变量不落库 |

## 3. 每张表字段详细设计

格式：**字段** / **类型** / **是否为空**（NO=非空）/ **注释**（取自 MySQL COMMENT）；约束单列每张表末尾。

### 3.1 sys_user — 系统用户（患者 & 管理员）

| 字段 | 类型 | 可空 | 注释 |
| --------------------------- | --------------- | --- | --------------------------------- |
| `id` | bigint unsigned | NO | 雪花主键，应用层生成 |
| `username` | varchar(32) | YES | 管理员登录账号；患者为空，唯一 |
| `phone` | varchar(20) | NO | 患者登录手机号，唯一 |
| `password_hash` | varchar(100) | NO | BCrypt 加密密文，不存明文 |
| `nickname` | varchar(50) | NO | 展示昵称，默认"用户" |
| `avatar_url` | varchar(500) | YES | 头像 URL |
| `user_type` | varchar(16) | NO | ADMIN 管理员 / PATIENT 患者，默认 PATIENT |
| `status` | tinyint | NO | 1 启用 / 0 停用（停用不能登录，数据保留） |
| `last_login_at` | datetime | YES | 最近登录时间 |
| `deleted` | tinyint | NO | 逻辑删除标记 |
| `created_at` / `updated_at` | datetime | NO | 创建 / 更新时间 |

**约束**：`PRIMARY KEY (id)`；`UNIQUE uk_user_username (username)`；`UNIQUE uk_user_phone (phone)`；`KEY idx_user_status_created (status, created_at)`。

### 3.2 patient_contact — 就诊人

| `user_id` | bigint unsigned | NO | 所属登录账号（sys_user.id） |
| `name` | varchar(50) | NO | 就诊人姓名 |

### 3.3 department — 科室（两级树）

| 字段 | 类型 | 可空 | 注释 |
| --------------------------- | --------------- | --- | ----------------------------------------------- |
| `id` | bigint unsigned | NO | 雪花主键 |

| `name` | varchar(100) | NO | 科室名称 |
| `parent_id` | bigint unsigned | NO | 上级科室 ID，**0 = 一级科室** |
| `department_type` | varchar(20) | NO | CLINICAL 临床 / MEDICAL_TECHNOLOGY 医技 / OTHER 其他 |

## 4. 关键设计决策与实施注意

1. **规则与号源分离**：排班规则是周期模板，患者只能对号源下单；扣库存只动 `schedule_slot`，规则表永不因预约改变。
2. **号源自动生成**：启动时 + 每天 00:10 把启用规则展开为未来 14 天号源，`uk_slot_doctor_date_time_level` 唯一键保证幂等；生成后失效号源查询缓存。
3. **订单快照**：医生姓名/科室名/号别名/金额/时间全部冗余进订单，历史数据不受基础资料变更影响。
4. **防超卖三层防护**：Redis 分布式锁（请求串行化）→ 号源 `version` 乐观锁条件更新（数据库兜底）→ 幂等键唯一约束（重试/重复点击兜底）；禁止"先查余号再更新"的竞态写法。
5. **无物理外键**：关联完整性由 Service 层校验 + 唯一/普通索引保证，降低逻辑删除与批量导入耦合。
6. **金额全链路分单位**：数据库、Java、JSON 一律整数分，前端只做"分→元"展示。
7. **大 ID 字符串传输**：雪花 ID 序列化为字符串返回，前端禁止 `Number()` 转换，否则超过 2^53 会精度丢失。
8. **JSON 字段边界**：`slots_json` 只存不参与查询过滤的时段配置；若未来需按时段统计，建议拆出独立时段表。
9. **超时取消**：RocketMQ 延迟消息驱动订单超时取消，消费端校验状态后取消并回补号源；NameServer 未启动时发送失败只记 warn 日志，定时兜底任务降频为 5 分钟一轮（超时取消 + 未支付提醒），订单事件在 MQ 不可用时直接落库站内信，双通道保证最终一致。

## 通用约定

1. **统一响应体**：所有接口返回 `ApiResponse<T>` = `{ "code": 200, "message": "操作成功", "data": T }`，`code=200` 成功，非 200 为业务错误码。
2. **分页响应体**：列表接口 `data` = `PageResult<T>` = `{ records: T[], total, page, size }`；分页参数 `page` 从 1 开始，`size` 默认 10。
3. **认证**：除注册/登录外，所有接口必须带请求头 `Authorization: Bearer <token>`：缺失/过期/已在 Redis 黑名单 → **401**；角色不匹配 → **403**。
4. **ID 传输**：雪花 ID 超过 JS 安全整数，后端一律以**字符串**返回，前端原样回传，**禁止转数字**。
5. **金额**：一律整数**分**，字段名带 `Fen`（如 `feeFen: 3000` = ¥30），前端 `/100` 转元展示。
6. **时间格式**：日期时间 `yyyy-MM-dd HH:mm:ss`、纯日期 `yyyy-MM-dd`、纯时段 `HH:mm:ss`（Asia/Shanghai）。
7. **删除**：管理端删除一律逻辑删除（`deleted=1`）/ 启停（`enabled=0`），不做物理删除。

# 04 Git 协作开发规范

> 远程仓库：Gitee `group-12-repo`，主分支 `master`

## 1. 分支策略

| 分支 | 用途 | 谁可推送 |
| --- | --- | --- |
| `master` | 主干，始终保持可编译、可演示 | 全员（合并后推送） |
| `feature/harmony-base` | 鸿蒙底座框架 | 底座负责人 |
| `feature/harmony-<名字/模块>` | 各人功能分支 | 分支负责人 |

**规则**：
1. 后端、Web 管理端开发期按模块天然隔离，直接在 master 上小步提交；鸿蒙端四人并行，走 feature 分支。
2. 每天开工前先 `git pull`；每天至少提交 1 次，下班前把 feature 分支合并回 master。
3. 合并顺序：先把 master 合进自己的 feature 分支解决冲突 → 本地编译验证 → 再合回 master。
4. 禁止 `git push --force` 到 master；禁止在没编译验证的状态下推送。

## 2. 提交信息格式

```
<类型>(<范围>): <一句话说明>
```

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| feat | 新功能 | `feat(后端+鸿蒙): 接入 DeepSeek AI 导诊` |
| fix | 修 Bug | `fix(鸿蒙): 修复雪花大ID精度丢失导致支付失败` |
| ui | 纯样式调整 | `ui(鸿蒙): 设置页字号放大、弹窗背景统一` |
| docs | 文档 | `docs: 更新接口文档` |
| merge | 分支合并 | `合并：成员C feature/harmony-wangyuyang 最新修复` |

## 3. 标准工作流（每天）

```bash
git pull                      # 1. 先拉最新
git checkout -b feature/xxx   # 2. 鸿蒙端开功能分支
# ...编码、本地编译验证...
git add <具体文件>
git commit -m "feat(范围): 说明"
git push origin feature/xxx
git checkout master && git pull
git merge feature/xxx
git push origin master
```

## 4. 冲突处理与排查方法

1. 冲突文件逐个看 `<<<<<<<` / `=======` / `>>>>>>>` 三段，理解两边各自改了什么再选，不要无脑选某一边。
2. 怀疑合并丢代码：`git diff <合并提交> <对方分支> -- <文件路径>`；`git log --oneline --graph --all`。
3. 解决冲突后必须完整编译一次再提交。

## 5. Redis 应用设计

| Key 模式 | 用途 | 策略 |
| --- | --- | --- |
| `his:cache:{function}:{key}` | 业务缓存 | Cache-Aside，TTL 5 分钟；数据增删改时主动删除 |
| `his:token:blacklist:{tokenId}` | 登出 Token 黑名单 | TTL = Token 剩余有效期 |
| `reg:lock:{就诊人}:{医生}:{日期}:{时段}` | 挂号分布式锁 | SETNX + 过期时间，防同一就诊人重复挂号 |
| `reg:limit:{userId}:{分钟}` | 挂号限流计数 | 每分钟最多 5 次 |

| `OrderTimeoutTask` | 每 5 分钟（兜底） | 超时未支付订单取消 + 5 分钟未支付提醒 |

## 8. 安全设计

1. 密码 BCrypt 加密存储。
2. 所有接口走 JWT 过滤器；患者/管理员双入口，角色不符返回 403。
3. 登出将 Token 加入 Redis 黑名单。
4. 挂号接口限流 + 分布式锁。
5. 身份证 AES-GCM 密文 + SHA-256 哈希，明文不回显。
6. 全局异常处理器兜底。

## 9. 前端架构要点（鸿蒙端）

- 分层：`pages/` → `api/` → `utils/request.ets` → `types/index.ets`。
- 状态管理：`store/UserStore.ets` 单例 + Preferences 持久化。
- 设计令牌：颜色/字号/间距/圆角集中在 `color.json` 与 `float.json`，禁止硬编码。
- 大 ID 规约：雪花 ID 按字符串接收与传递，禁止 `Number()`。

# 08 项目总结

> 项目：东软云医院预约挂号系统（鸿蒙 App + Web 管理端 + Spring Boot 后端 + DeepSeek AI 导诊）

## 1. 项目概况

面向患者与医院管理员的预约挂号系统。患者通过鸿蒙 App 完成挂号闭环并用 AI 导诊；管理员通过 Web 后台维护资源与处理订单。技术栈：Spring Boot 3 + MyBatis-Plus + MySQL 8 + Redis 7 + JWT，Vue 3 + Element Plus，HarmonyOS ArkTS/ArkUI，DeepSeek 大模型。

## 2. 已完成成果

| 模块 | 完成情况 |
| --- | --- |
| 患者端鸿蒙 App | 15 个页面，挂号全流程跑通；就诊人管理、设置、AI 管家可用 |
| Web 管理后台 | 工作台统计、用户/科室/医生/挂号级别/排班规则管理、挂号记录，共 7 个页面 |
| 后端服务 | 60 个 REST 接口，JWT 双角色鉴权，统一响应体与错误码，Knife4j 在线文档 |
| 号源体系 | 排班规则模板 + 号源自动生成（启动/每天 00:10/保存规则三触发，14 天窗口，幂等） |
| 并发与一致性 | 限流 + 分布式锁 + 幂等键 + 乐观锁四层防超卖；15 分钟超时自动取消；订单快照 |
| 缓存 | 科室树、号源查询 Cache-Aside，数据变更主动失效 |
| AI 导诊 | DeepSeek 接入，Function Calling 查真实号源，会话持久化 |
| 大 ID 兼容 | 雪花 ID 全链路字符串传输 |
| 账号资料管理 | 头像上传 + 昵称修改 |
| 身份证实名采集 | AES-GCM 加密 + SHA-256 哈希判重，脱敏回显 |
| 短信验证码 | 本地模拟，登录/找回密码 |
| 消息中心 | 站内信（预约成功/取消/超时/就诊提醒/未支付提醒），dedup_key 防重 |
| RocketMQ | 超时取消延迟消息、订单事件通知、5 分钟支付提醒，定时任务兜底 |

## 3. 技术亮点

- **规则与号源分离**：排班规则只做周期模板，号源自动滚动生成。
- **四层防超卖**：限流 → 分布式锁 → 幂等键 → 乐观锁。
- **订单快照设计**：历史订单不受基础资料变更影响。
- **无状态 AI 接入**：JDK 内置 HttpClient 直连 DeepSeek，Key 只存后端。
- **设计令牌统一**：鸿蒙端杜绝硬编码。

## 4. 踩坑与复盘

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 点"确认订单"无反应 | 雪花 ID 超过 JS 安全整数，前端精度丢失 | 后端 ID 字符串化，前端全链路 string 传递 |
| Git 合并后功能丢失 | 冲突解决误选旧代码 | `git diff` 逐文件对比合并结果与源分支 |
| Redis 缓存序列化异常 | 缓存了 MyBatis-Plus Page 对象 | 缓存只存 List 或普通 VO |
| 删除弹窗被拉全屏 | 弹窗容器有 layoutWeight | 移除 layoutWeight，外包撑满居中容器 |
| 弹窗底色不一致 | 不同弹窗分别设白/灰 | 统一 sheet_bg = #F1F3F5 |
| 构建内存不足 | 后端常驻占内存 | 构建时关闭后端进程 |
| 已支付订单无法取消 | 只允许待支付取消 | 放宽到待支付/已支付均可（已支付=退号） |
