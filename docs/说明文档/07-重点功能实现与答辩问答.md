## 二、规则校验类问题（老师挑刺型提问）

### Q1：身份证号有什么要求？全是 0 可以吗？能识别性别吗？
**答**：前后端都校验 18 位格式（前 17 位数字 + 末位数字或 X），就诊人身份证是选填项。全 0 这种"格式对但不是真证"的号**目前能通过**，因为我们只做了格式校验，还没做 GB 11643 校验位算法验证。性别识别目前也没做（数据库没存性别字段）——**优化方案**：身份证第 17 位奇偶判性别（奇男偶女）、7~14 位解析出生日期、第 18 位加权校验验真，这三个都能从现有 18 位直接推出来，加起来工作量很小，列入迭代计划。

### Q2：手机号有什么要求？全是 9 可以吗？
**答**：不行。注册和短信场景校验 `1[3-9]` 开头的 11 位标准手机号，99999999999 不满足第二位 3-9 的规则，会被拦。就诊人联系电话目前只校验"1 开头 11 位"（稍宽松），可以统一收紧成同一正则——这是已知的小优化点。

### Q3：密码有什么要求？有最大长度限制吗？必须含字母下划线吗？
**答**：只校验长度，没有复杂度要求。见各 DTO 的 `@Size` 注解：

| 场景 | 校验 | 要求 | 代码位置 |
| --- | --- | --- | --- |
| 患者注册 | `@Size(min=8, max=16)` | 8~16 位 | [AppRegisterRequest.java L20](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/dto/AppRegisterRequest.java#L20) |
| 患者登录 | `@Size(min=8, max=16)` | 8~16 位 | [AppLoginRequest.java L19](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/dto/AppLoginRequest.java#L19) |
| 找回密码 | `@Size(min=8, max=16)` | 8~16 位 | [SmsResetPasswordRequest.java L23](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/dto/SmsResetPasswordRequest.java#L23) |
| 管理员登录 | `@Size(min=6, max=16)` | 6~16 位（管理员放宽到 6 位，所以 `admin123` 能用） | [AdminLoginRequest.java L16](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/dto/AdminLoginRequest.java#L16) |

**没有**字母、下划线、数字、大小写等复杂度要求——`password`、`12345678`、`aaaaaaaa` 都能通过校验。上限控制在 16 位，防止超长输入攻击。后续可加 `@Pattern` 正则做密码强度校验（如必须含字母+数字），已列入迭代计划。

### Q4：有没有保存医生的剩余号？怎么保存的？
**答**：有。`schedule_slot` 号源表每条记录就是一个医生某天某时段的名额，`remaining_quota` 记剩余数，建表见 [01_schema.sql](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/resources/db/01_schema.sql) 的 `schedule_slot` 表；扣号用数据库条件原子 UPDATE（余量 > 0 + 乐观锁版本号），见 [OrderService.java L180-195](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L180-195)；取消回补 +1，见 OrderService 取消方法；查询加 Redis 缓存、扣号后按前缀失效，见 [OrderService.java L143-147](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L143-147)。

### Q5：同一个人同一时段能不能同时约两个医生？⚠️
**答（诚实版）**：防重复做了三层——同一就诊人 + **同一医生** + 同一日期同时段有 Redis 锁防并发重复下单，锁 key 见 [OrderService.java L114-129](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L114-129)；加上幂等键防重复提交，见 [OrderService.java L151-162](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L151-162)。所以"同一医生同一时段约两次"是不可能的。但**同一就诊人在同一天同一时段约不同医生**，目前没有做交叉拦截——正常用户一次流程只会选一个号，风险低，优化方案是下单前查该就诊人当天是否存在时段重叠的进行中订单，已列入迭代计划。

### Q6：两个人同时抢最后一个号会怎样？
**答**：两个人都通过限流和分布式锁（不同就诊人锁 key 不同，不互斥），进入数据库扣减——乐观锁保证同一时刻只有一个 UPDATE 成功，另一个 updatedRows=0 收到"号源已约满"，见 [OrderService.java L180-195](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L180-195)，不会超卖。

### Q7：15 分钟不支付会怎样？号源怎么处理？
**答**：RocketMQ 延迟消息 15 分钟后触发取消，下单时发延迟消息见 [OrderService.java L205-208](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L205-208)；取消是数据库条件更新（只有"待支付"状态会成功），号源 remaining_quota +1 回补，同时发"订单超时"站内信。MQ 没启动时定时任务兜底，见 [OrderTimeoutTask.java](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/task/OrderTimeoutTask.java)，效果一致。

### Q8：重复点支付/重复取消会怎样？
**答**：都是状态机条件更新（`WHERE status = '待支付'`），天然幂等。重复支付第二次影响行数为 0，直接返回当前订单详情不报错，见 [OrderService.java L207-223](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L207-223) 的 pay 方法（rows=0 且已支付直接返回）；重复取消抛"订单状态冲突"。不会出现扣两次钱或号源回补两次。

### Q9：支付是真的吗？
**答**：模拟支付。`payment_record` 支付流水表记录 INIT→SUCCESS 状态流转和模拟交易号，建表见 [01_schema.sql](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/resources/db/01_schema.sql) 的 `payment_record` 表；支付时 channel 固定写 `MOCK`，见 [OrderService.java L193-199](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/order/service/OrderService.java#L193-199)。支付接口与订单状态机解耦，接入微信/支付宝只需要替换支付渠道实现，订单侧不用动。

### Q10：退出登录后 token 还能用吗？服务重启 token 失效吗？
**答**：退出即把 token 的 jti 拉入 Redis 黑名单 `his:token:blacklist:{jti}`，立刻失效；黑名单在 Redis 不在内存，服务重启不丢。正常 token 在有效期内重启后依然可用（JWT 无状态设计）。登出逻辑见 AuthService.logout。

### Q11：验证码能被刷爆吗？
**答**：四层限制：60 秒冷却、同手机号同场景每日 10 条、验证码 5 分钟过期、连续错 5 次作废。限流逻辑见 [SmsCodeService.java L46-59](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/service/SmsCodeService.java#L46-59) 的 Redis 计数。

### Q12：验证码怎么实现的？接了真实短信吗？
**答**：本地模拟实现，不接真实短信通道，核心代码在 [SmsCodeService.java](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/service/SmsCodeService.java)。

**发送流程**（[L46-68](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/service/SmsCodeService.java#L46-68)）：
1. 60 秒冷却检查：`his:sms:{scene}:cd:{phone}` 存在即拒绝（防频繁请求）；
2. 每日 10 条上限：`his:sms:{scene}:daily:{phone}` INCR 计数，首次设 1 天过期，超 10 拒绝；
3. 生成 6 位随机码：`SecureRandom.nextInt(1_000_000)` 格式化 6 位；
4. 存 Redis：`his:sms:{scene}:code:{phone}`，5 分钟 TTL；
5. 打印日志：`log.info("[短信模拟] scene={} phone={} 验证码：{}")`——后端控制台看验证码（[L67](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/service/SmsCodeService.java#L67)）。

**校验流程**（[L73-97](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/service/SmsCodeService.java#L73-97)）：
1. 查 Redis 取存的验证码，不存在 = 已过期；
2. 不匹配：失败计数 +1（`his:sms:{scene}:fail:{phone}`），满 5 次直接作废验证码；
3. 匹配：删除验证码 + 失败计数（一次性消费，用完即废）。

**四层防刷总结**：

| 限制 | Redis Key | TTL |
| --- | --- | --- |
| 60 秒冷却 | `his:sms:{scene}:cd:{phone}` | 60 秒 |
| 每日 10 条 | `his:sms:{scene}:daily:{phone}` | 1 天 |
| 验证码 5 分钟有效 | `his:sms:{scene}:code:{phone}` | 5 分钟 |
| 错误 5 次作废 | `his:sms:{scene}:fail:{phone}` | 5 分钟 |

**接口入口**（[AppAuthController.java L57-94](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/auth/controller/AppAuthController.java#L57-94)）：`POST /sms/send`、`POST /sms/login`、`POST /sms/reset-password`，均在 SecurityConfig 的 `permitAll()` 白名单里，不需要登录就能访问。

## 三、数据库设计细节类问题

### Q19：sys_user 的 status 和 deleted 有什么区别？id 生成原理是什么？

**答**：两个字段职责完全不同，见 [01_schema.sql L25-42](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/resources/db/01_schema.sql#L25-42)：

| 字段 | 含义 | 取值 | 场景 |
| --- | --- | --- | --- |
| `status` | 账号**启用状态** | 1 启用 / 0 停用 | 管理员手动停用一个账号（如违规用户），停用后不能登录但数据保留，随时可重新启用恢复 |
| `deleted` | **逻辑删除标记** | 0 正常 / 1 已删除 | 管理端点"删除"时置 1，查询默认带 `WHERE deleted=0` 所以列表不可见；数据库物理记录保留，可追溯 |

简单说：**status 是"临时停用"，deleted 是"永久删除"**。停用可以恢复，删除（逻辑）后虽然数据库还在但业务上视为不存在。

**id 生成原理**：用 MyBatis-Plus 的雪花算法（`@TableId(type = IdType.ASSIGN_ID)`，见 [SysUser.java L15](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/user/entity/SysUser.java#L15)）。雪花算法由应用程序（不是数据库）生成 64 位整数 = **时间戳（41 位）+ 机器号（10 位）+ 序列号（12 位）**，好处是分布式下各自生成的 ID 不重复，为以后拆库分表留余地；不用数据库自增是因为自增 ID 拆库后会重复。

### Q20：patient_contact 的 id_card_cipher 和 id_card_hash 有什么区别和用途？

**答**：两个字段配合实现"加密存储 + 判重"，见 [PatientContact.java L46-53](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/contact/entity/PatientContact.java#L46-53) 和 [ContactService.java L114-124](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/contact/service/ContactService.java#L114-124)：

| 字段 | 算法 | 用途 | 为什么需要它 |
| --- | --- | --- | --- |
| `id_card_cipher` | AES-GCM 对称加密 | 存**密文**，需要时用密钥解密还原明文（如脱敏展示前先解密） | 明文绝不入库，密文可逆——只有持有密钥的后端能还原 |
| `id_card_hash` | SHA-256 哈希 | **判重**，同账号下同一身份证哈希一致即重复 | AES-GCM 每次加密带随机 IV，同一明文加密出的密文每次都不同，没法直接比对密文判重；哈希是确定性的，同一明文永远得到同一哈希，所以拿哈希做唯一索引判重 |

判重逻辑见 [ContactService.java L96-112](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/modules/contact/service/ContactService.java#L96-112)：按 `(user_id, id_card_hash)` 查询，有记录即抛"该身份证已绑定本账号的其他就诊人"。数据库唯一键 `uk_contact_user_idcard (user_id, id_card_hash)` 也兜底防并发重复绑定。

### Q21：doctor_registration_level 是不是医生的号别？可以同时多个号源吗？同一时段医生只能出一种号别怎么实现？

**答**：`doctor_registration_level` 是医生↔号别多对多关联表（一名医生可出普通号+专家号等多种号别），建表见 [01_schema.sql](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/resources/db/01_schema.sql) 的 `doctor_registration_level` 表。

**同一医生同一时段可以有多种号别的号源**——因为号源表 `schedule_slot` 的唯一键是 `uk_slot_doctor_date_time_level (doctor_id, visit_date, start_time, end_time, level_id)`，**level_id 在唯一键里**，意味着同一医生同一天同一时段可以有不同 level_id 的多条号源（比如同时放普通号 5 个 + 专家号 3 个）。

### Q26：直接插入的数据 id 是几位数，前端/鸿蒙端创建的 id 是很多位数字，怎么解释？

**答**：两种来源的 ID 本质不同：

| 数据来源 | ID 生成方式 | 位数 | 示例 |
| --- | --- | --- | --- |
| 种子 SQL（`02_demo_seed.sql`）直接 INSERT | SQL 里**手写固定小数字** | 4-5 位 | `2001`、`4002`、`70001` |
| 应用创建（前端/鸿蒙端调接口新增） | MyBatis-Plus 雪花算法（`IdType.ASSIGN_ID`）自动生成 | 18-19 位 | `2095770973474160642` |

种子数据手写小 ID 是为了演示直观（好记好查），但**生产/真实业务里所有 ID 都是雪花算法生成的 19 位长整数**。两种 ID 在数据库里都是 `BIGINT UNSIGNED`，类型一致可以混用；只是种子数据用小数字方便演示。雪花 ID = 时间戳(41位)+机器号(10位)+序列号(12位)，所以又长又不连续——这是分布式 ID 的正常表现，不是 bug。前端必须按字符串接收（见 Q14），否则 JS Number 精度丢失。

### Q28：JWT 鉴权怎么实现的？什么是 JWT？

**答**：JWT（JSON Web Token）是一种无状态的认证方案——服务端不存 session，token 本身携带用户信息+签名，服务端只验签名就能确认身份。

**JWT 三段式结构**：`Header.Payload.Signature`（以 `.` 分隔）
- Header：算法类型（HS256）+ token 类型（JWT）；
- Payload：用户数据（userId、userType、jti 唯一 ID、签发时间、过期时间）；
- Signature：用密钥对 Header+Payload 做 HMAC-SHA256 签名，**防篡改**——改了 Payload 签名就不匹配。

**本项目的 JWT 鉴权链路**：

| 步骤 | 位置 | 做的事 |
| --- | --- | --- |

**token 生成代码**（[JwtUtil.java L26-38](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/security/JwtUtil.java#L26-38)）：

```java
Jwts.builder()
    .id(UUID.randomUUID().toString())   // jti：唯一标识，用于登出拉黑
    .subject(String.valueOf(userId))      // sub：用户 ID
    .claim("userType", userType)         // 自定义声明：用户角色
    .issuedAt(now)                        // iat：签发时间
    .expiration(expireAt)                // exp：过期时间
    .signWith(secretKey())               // HS256 签名
    .compact();                           // 拼成 xxx.yyy.zzz
```

**为什么用 JWT 不用 Session**：
1. **无状态**：服务端不存 session，多实例部署不需要 session 共享（不像 Tomcat session 要配 sticky 或 Redis session）；
2. **移动端友好**：鸿蒙端/前端只需存 token 字符串，每次请求带头即可，不用管 Cookie；
3. **可扩展**：JWT 自带用户角色，不用查库就知道是谁、什么角色。

**登出怎么实现**：JWT 本身无状态，登出不能"撤销"token，所以用 Redis 黑名单——登出时取 token 的 `jti` 写入 `his:token:blacklist:{jti}`，TTL 设为 token 剩余有效期（见 [JwtUtil.extractMeta](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/java/com/neusoft/hisspringboot/security/JwtUtil.java#L53-59)），过滤器每次请求检查 jti 是否在黑名单。

**密钥配置**：`app.jwt.secret` 和 `app.jwt.expire-hours` 在 [application.yml](file:///d:/IDEA_Projects/test01/Hos_App/his-springboot/src/main/resources/application.yml) 配置，密钥用于签名+验签，泄露=任何人可伪造 token。
