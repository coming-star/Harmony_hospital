# 挂号并发控制与防超卖说明

> 版本：v1.0 ｜ 更新日期：2026-09-06
> 代码位置：`modules/order/service/OrderService.java`、`modules/order/task/OrderTimeoutTask.java`

挂号是全系统并发风险最高的操作：多人抢同一个号、用户狂点按钮、网络重试、超时未付占号。本系统用**四层防护 + 定时清理**解决，每层职责不同、缺一不可。

## 1. 防护总览

| 层级 | 手段 | Redis Key / 约束 | 拦截的问题 | 失败表现 |
| --- | --- | --- | --- | --- |
| ① 限流 | Redis 计数 | `reg:limit:{userId}:{yyyyMMddHHmm}` | 恶意/误触高频刷单 | 422001「操作过于频繁，请 1 分钟后再试」 |
| ② 分布式锁 | Redis SETNX，30 秒过期 | `reg:lock:{contactId}:{doctorId}:{visitDate}:{startTime-endTime}` | 同一就诊人对同一医生同一时段重复挂号（双击/并发） | 422001「请勿重复挂号」 |
| ③ 幂等键 | 数据库唯一约束 | `uk_order_user_idempotency(user_id, idempotency_key)` | 网络重试/重复提交生成多笔订单 | 返回已存在的同一笔订单 |
| ④ 乐观锁扣号 | 条件 UPDATE | `schedule_slot.version` + `remaining_quota > 0` | **真正的超卖兜底**：最后一个号被多人同时抢 | 409003「该时段已约满或状态已变化」 |

## 2. 各层实现细节

### ① 限流（每用户每分钟 5 次）

```java
String limitKey = "reg:limit:" + userId + ":" + yyyyMMddHHmm;   // 按分钟分片
long count = redisCacheUtil.increment(limitKey, 60);            // INCR + 60秒过期
if (count > 5) throw new BusinessException(..., "操作过于频繁，请 1 分钟后再试");
```

Key 按"分钟时间戳"分片，每分钟自动换一个计数器，无需滑动窗口。

### ② 分布式锁（防同一就诊人重复占号）

```java
String lockKey = "reg:lock:" + contactId + ":" + doctorId + ":" + visitDate + ":" + start + "-" + end;
boolean locked = redisCacheUtil.setIfAbsent(lockKey, uuid, 30); // SETNX + 30秒过期
if (!locked) throw new BusinessException(..., "请勿重复挂号（同一会诊人同一时段只能挂一个号）");
try {
    // 下单事务
} finally {
    if (uuid.equals(redis.get(lockKey))) redis.delete(lockKey); // value 匹配才删，防误删他人锁
}
```

注意锁的粒度是**就诊人 × 医生 × 日期 × 时段**，不是号源 ID：它防止"同一个人挂两遍同一个号"，而**不阻止不同人抢同一个号**——抢号的正确性由第 ④ 层乐观锁保证。锁设 30 秒过期是为了防止进程崩溃造成死锁。

### ③ 幂等键（防重试生成多单）

客户端每次进入下单页生成一个 UUID 作为 `idempotencyKey` 随请求提交。服务端下单前先按 `(user_id, idempotency_key)` 查订单：已存在则**直接返回原订单**，不重复扣号。配合数据库唯一约束，即使两个请求同时穿过查询也只会插入一笔。

### ④ 乐观锁扣号源（防超卖的核心）

```sql
UPDATE schedule_slot
SET remaining_quota = remaining_quota - 1,
    version = version + 1
WHERE id = ?
  AND status = 'OPEN'
  AND remaining_quota > 0
  AND version = ?;      -- 条件中带上读取时的版本号
```

- 影响行数 = 1：扣号成功，继续创建订单；
- 影响行数 = 0：号源已满 / 已停诊 / 版本号已被别人改掉 → 抛 409003。

**禁止**"先 SELECT 查余量、余量>0 再插订单"的写法——两个并发事务会同时读到余量 1，双双下单导致超卖。条件 UPDATE 把判断和扣减合成一条原子语句。

## 3. 号源归还（取消 / 超时）

库存归还同样用条件更新保证幂等：只有**本次 UPDATE 真正把订单状态改成 CANCELLED**（影响行数=1），才执行 `remaining_quota + 1, version + 1`；影响行数=0 说明订单已被别的路径取消/支付，不重复归还。

| 触发 | 入口 | cancel_reason |
| --- | --- | --- |
| 患者取消（待支付/已支付退号） | `POST /api/orders/{id}/cancel` | USER |
| 管理员取消 | `PUT /api/admin/orders/{id}/cancel` | ADMIN |
| 超时自动取消 | `OrderTimeoutTask`，`fixedDelay` 每 60 秒扫描 `expired_at < NOW() 且 status=PENDING_PAYMENT` | TIMEOUT |

待支付订单的 `expired_at = 下单时间 + 15 分钟`，由定时任务自动取消（当前版本用 `@Scheduled` 实现，未引入消息队列）。

## 4. 缓存一致性

下单扣号、取消归还后，都要失效号源查询缓存，否则患者端会看到过期余号：

```java
// 清掉"该科室 + 该日期"下所有视角（全部号别 / 指定号别）的缓存
redisCacheUtil.deleteByPrefix("his:cache:slotQuery:" + departmentId + "_" + visitDate + "_");
```

## 5. 为什么不能只靠其中一层

- 只靠分布式锁：锁有过期时间、且锁的是"就诊人重复"维度，挡不住不同人抢最后一号；
- 只靠乐观锁：能防超卖，但用户双击会生成两笔不同号源的订单、数据库也承受无效并发；
- 只靠幂等键：幂等键只在客户端复用同一 UUID 时有效，新请求绕不过；
- 只靠限流：限流是粗粒度防刷，正常用户 5 次内的并发仍然超卖。

四层各司其职，加上定时任务兜底清理过期占号，构成完整的并发防护体系。
