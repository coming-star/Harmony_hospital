# Git 提交规范与操作说明

> 负责人：成员 D（文档规范·Web 前端） | 日期：2026-08-31
> 目的：统一四人协作时的分支、提交信息与冲突处理方式，避免"提交记录看不出改了什么"或互相覆盖代码。

## 1. 分支策略

本项目当前阶段直接在 `master` 上开发，原因：组内 4 人、10 天工期，功能按模块（后端子包/前端页面）天然隔离，冲突概率低；开分支反而增加合并成本。约定：

- **每次开始改动前先 `git pull`**，确认本地是最新的再动手，减少冲突。
- 一次提交只做一件事：一个接口、一个页面、一份文档，不要把好几天的改动攒成一个大 commit。
- 涉及共享文件（`docs/07-RESTful接口契约.md`、数据库脚本、`SecurityConfig` 等基础设施）改动前，先在群里说一声，避免和别人正在改的内容冲突。

如果后续并行度上升、冲突变多，再切换到「每人一个 feature 分支 + 提交 PR」的模式，届时更新本文件。

## 2. 提交信息格式

```
<模块/接口简述>：<具体做了什么>
```

- 用中文，动词在前，说清楚"做了什么"，不用"fix bug"、"update"这类无信息量的话。
- 不需要 `feat:`/`fix:` 前缀（团队人数少，直接读中文描述更快）。
- 参考本项目已有提交：

  ```
  科室树查询接口：GET /api/departments/tree
  医生详情查询接口：GET /api/doctors/{id}，含挂号级别关联
  补全登录注册接口：JWT 登出与内存黑名单校验
  ```

- 文档类改动直接写清楚改了哪份文档、改了什么，例如：`修正接口契约：鉴权与查询接口路径/响应字段对齐实际实现`。

## 3. 提交前自查

- 后端：改动后本地跑一遍 `mvn -q compile`，确认能编译通过再提交。
- 前端：改动后跑一遍 `npm run build`，确认没有编译错误再提交。
- 不要把 `target/`、`node_modules/`、`dist/`、`.idea/`、本地 `.env` 等生成文件或私密配置提交进去；已在各自模块的 `.gitignore` 中排除，提交前用 `git status` 确认没有意外文件被加入。
- 涉及接口字段/路径变更，先同步更新 `docs/07-RESTful接口契约.md`，让其他人不用读代码也能知道契约变了。

## 4. 冲突处理

- `git pull` 出现冲突时，先看清楚冲突的是别人的哪次提交，不清楚就在群里问一句，不要盲目 `git checkout --theirs/--ours` 整个文件。
- 冲突解决后重新跑一遍编译/构建确认没有语义错误，再提交。

## 5. 日常操作速查

```bash
git pull                          # 开始改动前先拉最新
git add <具体文件路径>              # 不用 git add -A / git add .，避免误提交
git commit -m "模块：做了什么"
git push
```
